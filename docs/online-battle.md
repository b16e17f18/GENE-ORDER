# 通信対戦：第一工程（Node.js戦闘アダプター）

## 目的と今回の範囲

確定した最初のゴールは「固定レンタルPTを使い、合言葉で知人と対戦する」「6体見せ合い・3体選出」「技・能力値は固定」「戦闘結果はサーバーで確定」。本書の通信部分は設計案であり、未確定項目を実装済み仕様として扱わない。

今回は既存戦闘エンジンをNode.jsから再利用する橋渡しだけを実装した。部屋・通信接続・画面・認証・マッチング・本番サーバー契約・デプロイは未実装。既存の戦闘コード、正式CSV、AI、画面には変更を加えていない。main上に未コミットで保持する。

## 調査した既存コードと依存関係

| 既存ファイル／API | 確認事項・再利用方法 |
|---|---|
| battle-core.js の geneOrderBattle.createBattle | 初期編成、パッシブ、フォルム、陣営・共通フィールドを生成。randomを外から注入できる |
| battle-core.js の resolveTurn | 双方の行動をcheckActionで検証してから行動順と戦闘を処理する。通常の戦闘計算をそのまま再利用 |
| battle-core.js の continueSwitch | 溜め・技後交代・戦闘不能補充などの選択待ちから、停止していたターン処理を再開する |
| passive.js | 正式passive_typeマスタの検証・共通パッシブ効果・個体ごとの使用履歴を維持する |
| go-ui.js の createMatch | 入力を既存エンジンへ渡して、結果と演出用フレームを受け取る。描画と計算が分かれており、サーバーからUI本体をロードする必要はない |
| test/battle.test.mjs | 既存のNode VM実行・CSV正規化・シード対戦の方法を参考にした |
| app.js／data-validation.js | CSVパース・正式データ正規化・診断を再利用。app.jsのDOMContentLoadedコールバックは実行しない |
| dialogue-manager.js／battle-ai.js | app.jsのトップレベル生成とデータ検証のAI種別参照を満たすためロードする。対話画面・AIの行動選択は起動しない |

MHB用の旧グローバル関数ではなく、geneOrderBattleのAPIだけを呼ぶ。data-inline.jsは読まない。ブラウザ向けfetch、Image、localStorage、BGM、DOM描画は使わない。

## 実装したNode.js API

`server/battle-adapter.mjs`（Node.js 22以降、外部パッケージ不要）。信頼済みのリポジトリ内スクリプトをVMでロードする。VMを不正コードの隔離装置として使う設計ではない。root指定もサーバー運用側専用で、クライアントには指定させない。

```js
import { loadBattleAdapter } from './server/battle-adapter.mjs';
const adapter = loadBattleAdapter();
// 以下は技術検証用のID例。正式レンタルPTを新規登録するものではない。
const match = adapter.createBattle({
  player: ['character_001', 'character_002', 'character_003'],
  enemy: ['character_004', 'character_005', 'character_006'],
  seed: 91234, // テスト用。本番の秘密シードはサーバー側で生成する。
});
const result = match.resolveTurn({
  player: match.legalActions('player')[0],
  enemy: match.legalActions('enemy')[0],
});
if (result.pendingSwitch) {
  const { side, candidates } = result.pendingSwitch;
  // 実際の対戦では、そのプレイヤーから交代先入力を受け取って再開する。
  match.continueSwitch(side, candidates[0]);
}
const restored = adapter.replay(match.initial, match.history);
```

- 3体ずつの重複しない正式キャラクターIDで生成する。配列先頭が先発。ステータス・技・パッシブをリクエスト側から注入するAPIは設けない。未設定・使用可能技なし・不正なパッシブを持つ個体は拒否し、自動生成しない。
- eligibleCharacterIds()は検証に使える候補一覧。正式レンタルPTの定義や6体からの選出制限ではない。将来の部屋層で、サーバーが管理する固定6体から3体を選んだことを検証してからcreateBattleへ渡す。
- 共通のlegalActions/checkActionに従い、move・switch・合法な強制skipだけを受け付ける。任意waitや不正な追加フィールドは拒否する。両者が揃わない入力、不正な技・交代では状態と乱数を進めない。
- manualSwitches=trueで、続きの交代先を受け取るまで止まる。勝敗・EN費用・発動条件・行動順は既存エンジンが確定する。
- seededRandomは既存シード対戦同様に、random注入で既存の乱数判定を再現する。未指定シードは拒否し、0も許可する。Math.randomへの偶発的な依存はエラーにする。ダメージ乱数・通常急所などは追加しない。
- dataVersionは正式CSVの内容、engineVersionはロードした既存スクリプトとアダプター、rulesetVersionは両者をまとめたSHA-256。CSVまたは計算コードが変われば別ルールセットとなる。データ取得失敗時のMHBへのフォールバックはない。
- 初期条件、秘密シード、ルールセット識別子、受理したターン入力と交代再開入力を履歴として保持する。無効な入力は受理履歴へ追加しない。
- 戦闘ごとに正規化済みデータを複製し、別対戦やCSV正本を変えない。対戦途中にCSVを読み直さず、ロード時点の版を使う。

### 状態保存と公開の境界

battleはMap・相互参照・関数・交代待ちのgenerator継続を含む。JSON.stringifyだけでは永続化・復元できない。現段階の復旧手段は「同じルールセットを保持し、初期条件と受理済み入力履歴を先頭から再実行」。プロセス再起動後の永続ストレージ、原子的な履歴保存、署名・改ざん検知は未実装。

match.battle、initial、history、randomState、resolveTurnの生イベントはサーバー専用。隠された編成・能力・パッシブ・予約行動・乱数などを含み得るため、そのまま相手へ送信しない。go-ui.jsのcaptureFrameも描画用の内部状態であり、そのまま配信しない。今回のAPIはHTTP／WebSocket公開口ではない。

## 通信仕様案（未実装）

### 部屋と参加

サーバー管理のroomIdと合言葉で2人だけが入室し、接続ごとにサーバーが座席を割り当てる。メッセージ中のside指定を信用しない。状態案はwaiting → preview → selection → battle → finished。部屋の有効期限、合言葉の長さ・保管・総当たり対策、観戦可否、再入室トークン方式は未確定。アカウントやランキングは対象外。

### 固定レンタル・6体見せ合い・3体選出

固定レンタル6体の正式な組み合わせと管理ファイルは今後決定する。キャラクターの技・性能はサーバーの正式CSVから取得する。6体の見せ合いでは許可された情報だけを公開し、双方が3体と先発を確定するまで相手の選出や入力を秘匿する。確定後はその版を試合終了まで固定する。重複編成の可否（同種を6体内に複数置くか）、見せ合いで公開する技・パッシブ範囲、選出順の公開範囲は未確定。現アダプターの同じ対戦内3体のID重複は禁止。

### 行動の秘匿と同期

接続確立後のメッセージ案はbattleId・phase・turn・revision・requestIdと最小限の入力ID。双方の行動はサーバーで非公開に受け付け、揃ってからresolveTurnへ渡す。受信済みの表示だけを返し、相手の入力内容や入力で変わる評価は漏らさない。重複requestIdと古いturn/revisionの拒否、片方確定後の変更可否、入力の原子的受付は今後の部屋層で実装する。

交代選択待ちでは該当プレイヤーへ許可された候補だけを送り、continueSwitchで再開する。双方同時戦闘不能時はエンジンが順に選択待ちを返しても、一方の補充選択を他方の決定前に公開しない。両者確定を待つ入力バッファと配信タイミングを別途実装する。

演出の遅速やGIF再生はローカル表示に限定し、戦闘計算や入力期限に影響させない。初期は確認応答とrevisionで表示の追従を管理する案とし、演出中の次入力許可は未確定。

### サーバーの判定権限

所属・レンタルPT・選出・先発・合法行動・EN・技／パッシブ・行動順・乱数・命中・相性・ダメージ・状態異常・交代・勝敗はすべてサーバーで判定する。クライアントは行動IDを送信し、HP・ダメージ・能力値・判定結果を申告して確定させない。両者をserverのplayer/enemy席へ固定し、受信側の画面上の「自分／相手」へ変換する。

乱数シードや状態は相手へ送信しない。LCGは再現検証用で暗号学的な秘匿を保証するものではない。将来の不正対策要件に応じ、注入する乱数生成器を再検討する。外部通信はTLSを前提とするが、本工程では接続処理を実装していない。

### 公開状態と再接続

受信者別の公開状態を構築する専用層が必要。相手の未確定行動・未登場の選出3体・秘密シード・内部数値を含むbattle全体は配信しない。既存UIの相手HP実数非表示なども維持する。公開するHPの比率精度、EN、技使用履歴、能力評価ランク、ログの具体的な公開範囲は今後確定する。

切断を即敗北にはせず、同一座席への再接続と最新公開状態の再送に対応する方向で検討する。ただし、対戦を一時停止するか、受付済み両者の行動は処理するか、猶予・入力制限時間・時間切れの勝敗・双方切断の扱いは未確定。独断で待機・回避・降参に変換しない。プロセス障害時は保存済み入力履歴による復元が必要。
